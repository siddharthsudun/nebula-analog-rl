## 2. New: post-design qualification (`experiments/qualify_delivered.py`)

Runs the frozen delivered circuit and perturbations of it back through the **same** guard
path. Changes no recorded number — it characterises a circuit that already exists.

- **L1** single-parameter sensitivity, ±20% in 1% steps, per parameter
- **L2** pairwise interaction, 5×5 grid on the two tightest parameters
- **L3** bounded adversarial stress, `differential_evolution` inside a ±10% box, then
  bisection to the nearest failure
- Monte Carlo tolerance, σ = 10%/3, truncated at 3σ

L3 is labelled in the output as a **local heuristic** — worst case *found* in the budget,
not a proof of the global worst case — and its search objective uses the fast AC path, so
HD3 and noise do not steer it. Do not let that caveat get trimmed.

Smoke run (n=30) came back:

    binding (PVT)        dc_gain_db: worst corner 1.04 dB, floor 0.0 dB (slack 1.04 dB)
    local failure radius 19.0% (first: rs, breaks boost_db)
    L2 pairwise (rs x r_load)  1 of 25 grid cells fail
    L3 nearest failure   boost_db at max component 7.5%
    MC pass fraction     1.000  (95% CI 0.884 - 1.000, n=30)

**The full run is not finished.** `results/qualification_delivered.json` does not exist
yet. Re-run it:

```bash
PYTHONPATH=src .venv/Scripts/python -m silq.experiments.qualify_delivered --mc-n 10000 --de-maxiter 40 --de-popsize 12
```

## 4. LLM wrapper: it was inventing specs

`_heuristic` ran two regexes — first `<number> dB` anywhere, first `<number> mW` anywhere
— and on no match returned `Spec()`, every field at its default. The dashboard then
painted 9.0 dB / 12.0 dB onto the sliders as though it had read them out of the request.

Type "lets fuck" into the box and you got a confident spec back. That is the demo failure
mode: a judge types anything, gets an answer, tries a second string, gets the identical
answer.

Three fixes:

**It refuses what it cannot read.** `parse_spec_verbose` returns a `ParseResult` carrying
`recognised`; the endpoint 422s when that is empty; the UI leaves the sliders untouched
and says why. `silq.solve` refuses too and simulates nothing. The LLM path is instructed
to return `{}` rather than guess, and prose-instead-of-JSON is a failed parse.

**It reads the whole sheet.** Label-anchored, one line per pattern. The competition spec
sheet now yields 13 of 13 fields. Two ordering traps got caught in testing and both are
regression-worthy: "8.9 dB boost over a 14 dB channel" first parsed the channel as 8.9,
then after that fix parsed the boost as 14. Both gaps are now forbidden from crossing
another `dB`, and both word orders are tried in sequence.

**It says which fields actually do anything.** `pipeline.design()` takes exactly two
arguments. The other eleven parsed fields are enforced at `DEFAULT_SPEC`, not at what the
user typed. Every row is marked *applied to this run* / *matches the frozen default* /
*run enforces 15 mW*, with a red summary when a constraint is not honoured. Parsing
thirteen fields and implying all thirteen steer the search would be the same lie in a
nicer suit.

## 6. Open decision for whoever picks this up

Sid wants max power to be user-settable. He is right, and I did not build it.

The distinction that matters: **steering inputs** must reach the policy, which needs a
19th observation slot, which invalidates `seq_clean40k.zip` and means retraining — that
breaks the freeze and every benchmark number with it. **Acceptance constraints** do not
touch the policy at all, and `spec_for()` already returns a `Spec` that `hard_pass` is
evaluated against. Adding `power_w_max` to what `spec_for` overrides is close to a
one-line change.

So: power *can* be a user parameter, as a ceiling the result is judged against, never as
a target the search pursues. Set it to 1.5 mW and the run should come back
`closed_but_failed_verification`, `failing: ["power"]`. That is a useful answer.

Two things that must ship with it if it gets built:

1. The UI has to say the search does not optimise for these — otherwise we rebuild the
   illusion §4 just removed.
2. Any run with non-default requirements must be stamped, in the JSON and on screen, as
   *scored against user-modified requirements, not the competition specification*, with
   the diff listed. Without that it is a way to loosen power to 100 mW and declare
   victory.

Note `verify()` passes `DEFAULT_SPEC` to `build_evaluator` and the user spec only to
`hard_pass`. That is correct — guard thresholds are ours, requirements are the user's.
Keep it.

## 7. Known limitation I introduced

The conflict flag fires on **any** difference from the default, in either direction. Ask
for 20 mW — looser than the poster — and it goes red, though a run stricter than you
asked is harmless. It over-warns on the safe side. Directional would be better.

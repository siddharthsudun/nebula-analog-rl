Guard layer sandbox

Five tiers sit between raw SPICE output and any metric this project reports. Run one candidate design through the real evaluator and see exactly which tier it lives or dies on.

What is this checking, and why does it stop early?

src/eqrl/guards.py sits between the simulator and every downstream number. A run returns exactly one of two things: Valid (trusted metrics) or Invalid (exactly which check failed, and why) — there is no silent third option where a broken run reports a plausible-looking zero.

A single evaluation runs its tiers in order and stops at the first failure, so this page can only ever show you where a design died, not a full scorecard of all five:

  1. Run integrity — did the simulator actually exit cleanly and produce output?
  2. Circuit sanity — is the input pair in saturation, is the tail current the one requested, are node voltages inside the supply rails, is a device parameter pinned at a PDK bound?
  3. Corner integrity — do the process-corner model files actually differ from each other? A one-time startup check, not a per-design one — see the button below.
  4. Physical plausibility — is the DC gain, peaking, power, noise, HD3, and eye opening actually physically reachable — e.g. is "DC gain" secretly negative (an attenuator, not an amplifier) while "boost" (peak minus DC) inflates for free?
  5. Search pathology — watches a whole sequence of designs for suspicious patterns (parameters pinned at a range edge, identical metrics from different designs, reward rising while eye height falls). It has no meaning for one design evaluated in isolation, so it cannot be demoed here — see eqrl.guards.SearchMonitor if you want to read it.
